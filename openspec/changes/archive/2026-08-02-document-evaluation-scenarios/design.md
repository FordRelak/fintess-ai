## Context

Каждый каталог в `eval/scenarios/` объединяет raw input, нормализованные метрики, результат анализа, acceptance rules и результат evaluator. Сейчас эти роли можно восстановить только из имён файлов и исходного кода scripts. `scenario-001` будет первым документированным примером и основой для будущих scenarios.

## Goals / Non-Goals

**Goals:**
- Хранить общий Markdown-шаблон в `eval/scenarios/README.template.md` рядом с каталогами scenarios.
- Создать `eval/scenarios/scenario-001/README.md` по этому шаблону.
- Описывать цель проверки, сюжет данных, ожидаемое поведение, запрещённые утверждения, путь запуска и роли файлов.
- Явно разграничить нормативный `ground-truth.json`, пример валидного `result.json` и человеческое README.

**Non-Goals:**
- Не менять JSON schemas, `ground-truth.json`, `result.json`, normalizer или evaluator.
- Не делать README источником точных acceptance rules или заменой automated checks.
- Не создавать новый runtime-механизм для генерации README.

## Decisions

### Единый шаблон в каталоге scenarios

Шаблон хранится в `eval/scenarios/README.template.md`, а не в корневом README или в OpenSpec. Он относится к структуре evaluation data и находится рядом с каталогами, которые документирует.

Альтернатива: хранить шаблон только в `scenario-001/README.md`. Отклонена: будущему scenario пришлось бы копировать пример и отличать обязательную структуру от частного содержания.

### README описывает поведение, а не эталонный текст

Шаблон содержит раздел `Expected behavior` с наблюдениями, границами выводов и ожидаемыми действиями. `result.json` остаётся примером одного валидного результата; точные условия автоматической проверки остаются в `ground-truth.json`.

Это допускает разные корректные формулировки анализа без потери воспроизводимости проверки.

### Минимальная стабильная структура

Шаблон задаёт разделы: цель, сюжет, данные, ожидаемое поведение, недопустимые утверждения, путь проверки, критерий успеха и роли файлов. Scenario может добавить свой раздел, если это улучшает понимание, но не должен удалять разделы, объясняющие контракт проверки.

### Разделение инструкции и результата запуска

README содержит команды для повторного запуска normalizer и evaluator, но не фиксирует текущий статус проверки как нормативный. `evaluation.json` остаётся снимком конкретного запуска; `manual_review` допустим, когда automated checks не содержат `failed`.

## Risks / Trade-offs

- [Шаблон станет слишком жёстким для нового типа scenario] → Сохранить обязательные общие разделы и разрешить дополнительные scenario-specific разделы.
- [README продублирует и рассинхронизируется с `ground-truth.json`] → Документировать смысл правил, но не копировать списки matcher-значений и точные policy.
- [Команды в README устареют] → Использовать фактические CLI-интерфейсы `Normalize.cs` и `Evaluate.cs`, не добавлять shell-обёртки.
